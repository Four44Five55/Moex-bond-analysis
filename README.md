# MOEX Analytics — анализ облигаций и акций

Веб-приложение для анализа инструментов Московской биржи (облигации и акции):
детальный анализ, поиск, фильтрация, графики исторических цен, избранное и сравнение,
а также учёт собственного портфеля — сделки, позиции по FIFO, аллокация, доходный
календарь, налоги и доходность XIRR.

## Стек

- **Backend:** Java 21, Spring Boot 3.4 (Web, Data JPA, Data Redis, Cache, Validation), PostgreSQL 16,
  Redis 7, Flyway, OkHttp, Apache POI, springdoc/OpenAPI. Тесты: JUnit 5 + Testcontainers.
- **Frontend:** React 18 + TypeScript + Vite, TanStack Query, React Router, lightweight-charts.
- **Инфраструктура:** Docker Compose (Postgres + Redis).

## Архитектура (backend, слоистая / hexagonal-lite)

```
web            REST-контроллеры v1, DTO (records), маппер, обработчик ошибок, OpenAPI
application    use-cases/фасады: InstrumentService, SyncService, CandleService,
               WatchlistService, ExportService, AccountService, TransactionService,
               PortfolioService; события (Observer)
domain         модель (Instrument→Bond/Share, Candle, WatchlistItem, Account, Transaction),
               money/* (Money — масштабы, округление, безопасное деление),
               analysis/* (доходности, дивиденды, скоринг), фильтры (Specification),
               portfolio/* (FIFO, прогноз выплат), portfolio/tax/* (стратегии НДФЛ),
               portfolio/allocation/* (измерения), portfolio/history/* (ряд стоимости, XIRR),
               порты (MarketDataProvider, CandleProvider, CorporateActionsProvider)
infrastructure адаптеры: moex/* (клиент+парсеры), persistence/* (Spring Data JPA),
               cache/* (Redis), scheduler/* (синхронизация)
```

**SOLID:** SRP (парсер/анализатор/репозиторий/контроллер раздельно), OCP (новый тип = новая стратегия),
LSP (Bond/Share ↔ Instrument), ISP (узкие порты), DIP (домен зависит от портов, реализации — в infrastructure).

**Паттерны GoF:** Strategy (парсеры/скоринг по типу, стратегии НДФЛ, измерения аллокации),
Abstract Factory / Adapter (MOEX-клиент), Factory Method (`TaxStrategyFactory`, `AllocationDimensionFactory`),
Template Method (поток загрузки MOEX, `AbstractTaxStrategy`), Builder (`PortfolioValueRequest`),
Repository + Specification (динамические фильтры), Facade (`InstrumentService`, `PortfolioService`),
Observer (`DataRefreshedEvent`), Decorator/Proxy (Spring Cache поверх портов).

**Конкурентность:** облигации и акции загружаются параллельно (`CompletableFuture` + выделенный пул),
свечи кешируются (cache-aside: PostgreSQL → MOEX), горячие ответы — в Redis; планировщик `@Scheduled`
периодически синхронизирует данные и сбрасывает кеши через событие.

### Деньги — `BigDecimal`, аналитика — `double`

Учётный контур (сделки, комиссии, движения денег, вклады, FIFO, налоги, суммы и итоги портфеля)
считается в `BigDecimal`. Причина простая: суммы по счёту — это свёртка сотен операций, а двоичная
дробь не представляет точно даже 0.10 ₽. На одной сделке расхождение незаметно, в налоговой базе
и внесённом капитале оно вылезает копейками, которые не сходятся с отчётом брокера.

Политика собрана в `domain/money/Money`: три масштаба (2 — итоговые суммы, 6 — величины на одну
бумагу, 12 — промежуточные деления), округление `HALF_UP` (как при удержании НДФЛ), безопасное
деление и `pct`. Тип поля остаётся голым `BigDecimal` — без своего value-объекта и без JavaMoney
(JSR-354) / Joda-Money: обе библиотеки решают в первую очередь мультивалютность, которой здесь нет,
а платить за них пришлось бы JPA-конвертерами на каждое поле и нестандартным JSON (фронт получал бы
объект вместо числа).

**Что осознанно осталось `double`:**

| Остаётся `double` | Почему |
|---|---|
| XIRR, YTM, дюрация, выпуклость | решение уравнений через `Math.pow` с дробной степенью; точной десятичной арифметики для них не существует, результат иррационален |
| свечи OHLCV, `lastPrice`, изменение за день, капитализация | котировки приблизительны по своей природе и меняются ежесекундно |
| проценты и доли (`unrealizedPct`, `percent` в аллокации) | производные величины для показа, округляются до десятых |
| дневной ряд стоимости (`portfolio/history/*`) | строится по свечам, то есть уже из `double` |

Граница односторонняя и явная: деньги уходят в аналитику через `Money.toDouble`, котировка входит
в денежный расчёт через `Money.of`. Единственное место, где эти миры встречаются, — `InstrumentPricing`.

**Грабли:** сравнивать суммы только через `compareTo` (для нуля — `Money.isZero`) — `equals` у `BigDecimal`
учитывает масштаб, и `100.00` не равно `100.000000`. В тестах по той же причине
`isEqualByComparingTo`, а не `isEqualTo`. Ещё: у примитивного `double` значение по умолчанию
было `0`, у `BigDecimal` — `null`, поэтому денежные поля сущностей инициализированы `Money.ZERO`
явно, иначе сделка без комиссии падала бы на `NOT NULL`.

Схема: миграция `V8` переводит денежные колонки из `DOUBLE PRECISION` в `NUMERIC`
(19,6 — на бумагу; 19,2 — суммы; 9,4 — ставки). Котировки и метрики остаются `DOUBLE PRECISION`.

### На что легко наступить

**Чтение свечей — операция записи.** `CandleService.getCandles` работает по cache-aside: недостающие
отрезки периода догружаются из MOEX и сохраняются в БД. Сервисы же помечены `@Transactional(readOnly = true)`
на уровне класса, а вложенный `@Transactional` при распространении `REQUIRED` присоединяется к внешней
транзакции и её read-only не отменяет — PostgreSQL отвергнет INSERT. Поэтому любой публичный метод,
который вызывает `CandleService`, обязан перекрыть транзакцию своим `@Transactional`: так сделано
в `InstrumentService.performance` и `PortfolioService.valueSeries`. Модульные тесты это не ловят.

**Свечи не перезапрашиваются целиком.** Хвост периода догружается **включая** последнюю сохранённую
дату: свеча текущего дня пишется незакрытой и должна перезаписаться. На таблице `candle` висит
`UNIQUE (sec_id, interval_code, ts)`, поэтому между удалением отрезка и вставкой стоит явный
`flush()` — иначе Hibernate выполнит INSERT раньше DELETE и нарушит ограничение.

**Примитивное поле сущности ⟹ колонка `NOT NULL`.** Прочитав `NULL` в поле типа
`double`/`int`/`boolean`, Hibernate бросает «Null value was assigned to a property of primitive
type» и отдаёт 500 на *любой* строке таблицы, а не только на испорченной. Так однажды слегла вся
выдача облигаций: `V3` добавила `bond.accrued_interest` как nullable без `DEFAULT`, и всем 3099
уже загруженным выпускам туда встал `NULL` (починено в `V4`, остальные такие колонки закрыты `V9`).

Мина взводится не при вставке, а в момент `ALTER TABLE ADD COLUMN`: значение появляется только
у новых строк, а старым достаётся `NULL`. Поэтому зелёными остаются оба обычных способа проверки —
модульные тесты гоняются на пустой базе, а свежий `docker compose up` создаёт схему с нуля.
Ломается ровно та инсталляция, где приложение уже работало. `ddl-auto: validate` тоже не помогает:
Hibernate сверяет существование колонок и типы, но **не nullability**.

Инвариант держит `PrimitiveColumnsAreNotNullIT` (в задаче `integrationTest`): он обходит все
`@Entity`, и для каждого примитивного поля проверяет `information_schema.columns`. Колонку, которую
не удалось сопоставить, тест не пропускает молча, а валит — иначе он был бы зелёным именно там,
где ничего не проверил.

Если тест покраснел, вопрос один: **«значения нет» — осмысленное состояние?** Если да, поле должно
стать обёрткой (`Double`/`Integer`), а колонка остаться nullable — так сделано для `ytm`, `duration`,
`convexity`, `couponFrequency`, `listLevel`, `reliabilityScore`: у выпуска без сделок доходности
и дюрации действительно нет, и ноль вместо них не нейтрален — он проходит фильтр «дюрация не больше
N» и встаёт в сортировку по доходности как настоящее значение. Если нет — миграция приводит колонку
к `NOT NULL DEFAULT` с backfill существующих строк, как в `V4` и `V9`.

## Запуск

Порты подобраны без конфликтов: backend **8090**, frontend dev **5180**, Postgres **5445**, Redis **6380**.

```bash
# 1. Инфраструктура
docker compose up -d

# 2. Backend (http://localhost:8090, Swagger UI: /swagger-ui.html)
cd backend
./gradlew bootRun        # при пустой БД выполнит стартовую синхронизацию с MOEX

# 3. Frontend (http://localhost:5180)
cd frontend
npm install
npm run dev
```

**Свободные деньги** не хранятся полем, а выводятся из истории: пополнения − выводы − покупки −
комиссии + продажи + полученные выплаты. Поле-остаток пришлось бы синхронизировать с каждой сделкой,
и оно бы разъезжалось.

**Внесённое, вложенное и полученное — три разные величины, и складывать их нельзя.**
`externalIn` — деньги, пришедшие извне (пополнения − выводы, плюс тело вкладов в сводке);
`invested` — себестоимость открытых позиций, которая растёт и от реинвестированных выплат,
без единого нового рубля; `receivedIncome` — все полученные купоны и дивиденды, из которых
реинвестированные уже сидят внутри `invested` и `marketValue`. Поэтому «вложено + получено»
капиталом не является, а итог сходится по одному тождеству: `totalProfit = totalValue − externalIn`.
Переоценка, прибыль от продаж и выплаты — источники этой суммы, а не добавка к ней.
Если хотя бы по одному счёту со сделками нет движений денег, `externalIn` и `totalProfit`
приходят `null`: неизвестно — это не ноль.

Пока по счёту **не заведено ни одного движения денег**, остаток считается неизвестным и берётся
нулём (`CashBalanceCalculator.reportedBalance`). Иначе счёт со сделками, но без пополнений — а так
выглядит любой счёт, созданный до появления учёта денег, — показывал бы «свободные деньги» в размере
минус всех покупок, занижал на ту же сумму весь капитал, а в XIRR покупки вычитались бы дважды:
один раз потоками по сделкам, второй — тем же минусом в завершающем потоке.

Учёт денег меняет смысл **XIRR**. Если по счёту заведены пополнения, доходность считается от них:
покупка бумаги на уже заведённые деньги — не вложение капитала, а перекладывание внутри портфеля,
и включать её в потоки нельзя, иначе доходность растёт от одного лишь оборота. Если движений денег
нет (так выглядит любой счёт, заведённый до появления их учёта), остаётся прежний расчёт по сделкам —
иначе у таких счетов XIRR просто исчез бы. Практический вывод: **чтобы увидеть честную доходность,
заведите пополнение на сумму, с которой начинали.**

У вклада можно указать **счёт-источник** (`sourceAccountId`, миграция `V7`) — тогда его тело
уходит из свободных денег этого счёта, не считается внесённым извне и не даёт отдельного потока
в XIRR: перевод с брокерского счёта — движение внутри портфеля, а те деньги уже учтены его
пополнением. Без источника вклад считается открытым деньгами со стороны, как раньше.

**Вклады** привязаны к клиенту, а не к брокерскому счёту: у них нет сделок, бумаг и котировок.
Стоимость на любую дату — детерминированная функция (`DepositCalculator`, ACT/365): тело плюс
проценты, которые начислены, но ещё не выплачены — тот же принцип, что НКД у облигации.
У капитализируемого вклада проценты не покидают вклад и сидят в его стоимости; у обычного —
уходят владельцу и в стоимости не остаются.

**Налог по вкладам считается на уровне клиента, а не вклада**: необлагаемый вычет
(1 млн ₽ × максимальная ключевая ставка за год) даётся один раз на все вклады сразу, поэтому
посчитать налог по каждому и сложить — значит выдать вычет столько раз, сколько вкладов.
Ключевая ставка берётся из веб-сервиса ЦБ (`cbr.service-url`, SOAP-метод `KeyRate`) — в MOEX ISS её
нет. Ряд ставок приходит **без выходных**: записи ровно за 1 января или 1 мая в нём может не быть,
поэтому ставка «на 1-е число» ищется как последняя известная на дату не позже первого числа.
Ответ кешируется на 12 часов. Если ЦБ недоступен, берётся `app.tax.key-rate-fallback-pct`
(переменная `KEY_RATE_PCT`) — сводка по капиталу из-за недоступности ЦБ падать не должна.

Пять эндпоинтов от `positions` до `tax` считаются из одного снапшота портфеля, но каждый строит его
заново — это отдельный прогон FIFO и отдельный обход выплат на каждый вызов. Страница счёта поэтому
ходит в `/overview`; частные эндпоинты оставлены для интеграций, которым нужен один кусок.

## Аналитика инструмента и портфеля

Финансовые расчёты вынесены в отдельные чистые классы домена (`domain/analysis`, `domain/portfolio`) —
без БД и сети, тестируются изолированно; бэкенд считает, фронт только отображает.

- **Доходности инструмента** (`ReturnsCalculator`): изменение за 1Д/1Н/1М/1Г/YTD и 52-нед. диапазон из дневных свечей.
- **Метрики облигации**: НКД и дата оферты дочитываются из MOEX (миграция `V3`); текущая доходность — производная модели `Bond`.
- **Дивидендная доходность акции** (`DividendYieldCalculator`): сумма выплат за 12 мес / цена.
- **Аллокация портфеля** (`AllocationDimension` + `AllocationDimensionFactory` + `AllocationCalculator`):
  разбивка по типу/сектору/валюте. Измерение — паттерн **Strategy**; новое измерение = новый бин (**OCP**),
  фабрика собирает их списком автоматически.
- **Оценка позиции — по грязной цене** (`InstrumentPricing.currentPositionMoneyPerUnit`): чистая
  котировка плюс НКД. Себестоимость лота уже содержит НКД, уплаченный продавцу при покупке, поэтому
  оценка по чистой цене показывала бы убыток ровно в его размере сразу после сделки — и держала бы
  его до выплаты купона.
- **Позиции и P&L** (`FifoCalculator`): свёртка сделок по FIFO — открытые лоты и реализованные продажи,
  комиссии распределяются на единицу. Даты покупки/продажи сохраняются: по ним считается ЛДВ.
- **Прогноз выплат** (`IncomeForecaster`): купоны и амортизации по графику MOEX; дивиденды —
  только с объявленной датой отсечки. Прикидка «по прошлогодней выплате» намеренно не строится:
  для разовых выплат она вводит в заблуждение.
- **Достраивание графика купонов** (`CouponScheduleEstimator`): у облигаций с плавающей ставкой
  биржа знает сумму только текущего и прошедших периодов — у ОФЗ-ПК 29026 это 6 купонов из 55.
  Раньше такие строки отбрасывались, и флоатер исчезал из календаря выплат, прогноза дохода
  и купонной базы налога целиком. Теперь незафиксированные купоны оцениваются по ставке последнего
  известного — на их собственные номинал и длину периода, поэтому амортизация номинала и разная
  длина периодов учитываются сами собой — и помечаются флагом оценки, который доходит до интерфейса
  (знак `≈`). В отличие от дивидендов, здесь оценка честна: действующая ставка объявлена,
  неизвестен только её будущий дрейф.
- **Календарь выплат** (`PaymentCalendarCalculator`): купоны, амортизации, дивиденды и проценты
  по вкладам, разложенные по месяцам горизонта с разбивкой по видам. Все суммы — **будущие
  поступления**, а не начисленное: в календарь входят выплаты с сегодняшнего дня и дальше,
  поэтому текущий месяц показывает только ещё не выплаченное. Возврат номинала по амортизациям
  выделен отдельно от дохода (`principalReturn` против `incomeGross`): деньги приходят, но это
  возврат вложенного, а у портфеля с амортизируемыми выпусками он легко больше самих купонов. Месяцы без выплат остаются
  в ответе с нулями — провал в календаре и есть то, ради чего его смотрят, а среднемесячный доход
  делится на весь горизонт, а не на месяцы с выплатами, иначе регулярность дохода завышается.
  Горизонт — параметр (до 60 мес): облигационная лестница видна только на нескольких годах.
- **НДФЛ** (`TaxStrategy` + `AbstractTaxStrategy` + `TaxStrategyFactory`): брокерский счёт, ИИС типа А и Б —
  **Strategy** поверх **Template Method**. Прогрессия 13/15% от порога, ЛДВ при владении ≥3 лет.
  Ставки лежат в `TaxRates` — единственном источнике истины и для налога, и для оценки выплат «на руки».
- **Стоимость портфеля во времени** (`PortfolioValueCalculator` + `PortfolioValueRequest` — **Builder**):
  дневной ряд «рыночная стоимость / вложенный капитал». Сделки прокручиваются по календарю одним
  проходом — O(дней + сделок). Котировки облигаций приводятся из процентов от номинала в рубли
  (`InstrumentPricing.moneyPerUnit`). Свечи запрашиваются с запасом в две недели до начала периода:
  цена берётся по ближайшему предшествующему торговому дню, и если период начинался в выходные,
  ряд стартовал с нулевой стоимости. Бумага, по которой свечей нет вовсе, идёт по последней
  известной цене ровной линией — иначе её стоимость была бы нулём при живой сумме во «вложено».
- **Доходность XIRR** (`XirrCalculator`): метод Ньютона с откатом на бисекцию — на реальных потоках
  Ньютон расходится (производная NPV вырождается, шаг выбрасывает ставку за `r ≤ −1`), бисекция
  сходится гарантированно. В потоки входят все сделки за историю счёта, полученные выплаты
  и текущая стоимость позиций как терминальный поток.

На фронте переиспользуемые графики живут в `shared/charts` (кольцевая диаграмма аллокации,
столбцы выплат с накоплением по видам, многорядный линейный график).

## Тесты

```bash
cd backend && ./gradlew test              # модульные тесты, Docker не нужен (~15 c)
cd backend && ./gradlew integrationTest   # тесты на Testcontainers, нужен запущенный Docker
cd frontend && npm run build              # проверка типов + сборка
```

Покрыты все чистые калькуляторы домена (доходности, дивиденды, FIFO, налоги, аллокация,
прогноз выплат, ряд стоимости, XIRR), сериализация кеша и загрузка контекста приложения.

Классы `*IT` вынесены из `test` в отдельную задачу `integrationTest` и не входят в `check`:
они поднимают PostgreSQL в Testcontainers, и при выключенном Docker сборка падала бы при
полностью исправном коде. `ApplicationContextIT` поднимает полный контекст приложения —
остальные тесты модульные, и без него рассинхрон конструкторов или недостающий бин
всплывали бы только в рантайме. Redis ни там, ни там не требуется.

## Замечание по данным

У MOEX ISS нет прямого кредитного рейтинга — надёжность облигаций оценивается прокси-эвристикой
(уровень листинга + признак ОФЗ) в `ReliabilityScorer`; заменяется на реальный источник без изменения
остального кода. Аномальные доходности (YTM в сотни %) помечаются флагом `suspiciousYield` и по умолчанию
исключаются из выборок и сводок.

**НКД на дату сделки берётся у биржи, а не считается.** Рассчитать его по графику купонов можно
только для фиксированной ставки: у флоатера сумма будущего купона не зафиксирована, и делить её
по дням не из чего. Зато `ACCINT` в истории торгов
(`/history/engines/stock/markets/bonds/securities/{secId}.json`) есть по каждому торговому дню
и для флоатеров тоже — оттуда форма ввода сделки и подставляет НКД (за сегодня — из справочника,
он уже загружен синхронизацией). Ответ кешируется по паре «бумага + дата»: за прошедший день
значение не изменится. Если MOEX недоступен, поле остаётся пустым для ручного ввода — ввод сделки
не должен зависеть от внешнего сервиса.

Сделки, заведённые до появления автоподстановки, дозаполняются кнопкой на странице счёта
(`POST /accounts/{id}/transactions/backfill-aci`). Она трогает только сделки с нулевым НКД —
там, где значение вписано руками, биржевое ничего не улучшит, а перезапись потеряла бы правку —
и работает в два шага: сначала примерка со списком изменений и суммой, потом запись.
Комиссии при этом не пересчитываются: это фактически уплаченные деньги, а не производная величина.

Котировки облигаций MOEX выражены **в процентах от номинала**, а дюрация приходит **в днях**
и в блоке `marketdata`, а не `securities`. Один выпуск отдаётся на нескольких режимах торгов —
парсер дедуплицирует по `SECID`. Везде, где облигация оценивается в рублях, цена проходит через
`InstrumentPricing.moneyPerUnit`.

**Бессрочные выпуски не попадают в выборку.** `MoexBondParser` отбрасывает бумаги без `MATDATE`
(вместе с настоящим мусором в сырых данных), а у перпетуальных облигаций даты погашения нет
по определению. Расчёты доходности и дюрации на них тоже опираются, поэтому это осознанный
компромисс, а не недосмотр: поддержка потребует отдельной ветки в анализе, а не только правки фильтра.

## Ограничения

**Аутентификации нет.** `X-Client-Id` — это UUID из localStorage браузера, а не учётная запись:
сервер принимает заголовок на веру. Изначально так было устроено анонимное избранное, но теперь
за тем же заголовком лежат счета, сделки и налоги — любой, кто знает чужой UUID, получит доступ
к этим данным. Приложение рассчитано на локальный/личный запуск; перед выкладыванием наружу
нужна настоящая аутентификация.

**Расчёты — оценочные.** Налоги считаются по упрощённой модели (прогрессия, ЛДВ, тип счёта)
и не учитывают сальдирование убытков между счетами, вычеты ИИС типа А и валютную переоценку.
Это ориентир, а не налоговая отчётность.
